# Constitution — Architecture Decision Records

Append-only log. Each ADR: **Context** (why the decision exists), **Decision**, **Consequences**, **Revisit trigger** (what would justify changing it). Superseded ADRs are marked, never deleted.

---

## ADR-001 — A dedicated `constitution` schema

**Status:** Accepted (retroactively documented). **Context:** The Enterprise Constitutional AI layer is a distinct product from the OwnerPilot notice platform (`public`), with its own lifecycle, security posture, and 59-table surface. **Decision:** Keep it in a separate Postgres schema (`constitution`) in the same Supabase project, isolated from `public`. **Consequences:** clean namespace + independent RLS posture; but it shares the production instance (blast-radius awareness needed) and needs its own drift/validation tooling (the `public` tooling is schema-scoped). **Revisit if:** the layer needs independent scaling/failure isolation → promote to its own database/project.

## ADR-002 — Database-first origins → repository-first going forward

**Status:** Accepted. **Context:** `constitution` evolved directly in production with no source control; `public` is fully repo-driven. Database-first is invisible to review, drift checks, and Advisors. **Decision:** Freeze the database-first era with a documented baseline (Phase B) and require every future change to flow through the repository-first workflow (Phase F). Production remains source of truth *only until* the baseline is exported and adopted. **Consequences:** one-time reverse-engineering + baseline cost; afterward, full reviewability. **Revisit if:** never — repository-first is the target end state.

## ADR-003 — Security model: deny-by-default, operator-plane access

**Status:** Accepted. **Context:** constitutional data (strategy, decisions, governance) is sensitive and not owner-facing. **Decision:** RLS enabled on all tables, **no permissive policies** (deny-by-default); access is `service_role`/owner only; the schema is not PostgREST-exposed. **Consequences:** anon/authenticated cannot reach it even if the schema were exposed; all access flows through server/operator context. **Revisit if:** a genuine end-user read surface is introduced → add *scoped* policies via ADR, never `USING (true)`.

## ADR-004 — RLS strategy: enable + no policy (not permissive policies)

**Status:** Accepted. **Context:** two ways to lock a table — RLS-with-restrictive-policies or RLS-enabled-with-no-policy. **Decision:** RLS enabled, **zero policies** = implicit deny-all, matching all 59 tables (and the same fail-closed posture the `public` audit/cron tables use). **Consequences:** simplest correct lockdown; Supabase Advisors reports these as `rls_enabled_no_policy` INFO (expected, not a defect). **Revisit if:** a table needs row-scoped access → add a specific policy, documented, never a blanket true.

## ADR-005 — SECURITY DEFINER functions with pinned search_path

**Status:** Accepted. **Context:** business logic (scenario generation, scoring, champion selection, recommendation build, discovery) must run with elevated, deterministic privileges regardless of caller. **Decision:** those functions are `SECURITY DEFINER`, `plpgsql`, **always** `SET search_path TO 'constitution','public'` (+`pg_catalog` where needed), with row locks / advisory locks for concurrency. Current allow-list: `build_decision_recommendation`, `generate_scenario_set`, `run_supabase_discovery`, `score_strategy_candidate`, `select_strategy_champion`. **Consequences:** safe elevation without search-path hijack; every new SECURITY DEFINER function must be added to this allow-list + reviewed (validation check #4). **Revisit if:** a function no longer needs elevation → downgrade to INVOKER.

## ADR-006 — Enterprise Simulation architecture (ESL-002/003/004)

**Status:** Accepted. **Context:** strategy decisions must be evidence-backed against generated scenarios and simulated actors. **Decision:** a pipeline — scenario generation (seeded, deterministic) → actor/behavioral/negotiation state → strategy candidates evaluated per-scenario with metric/constraint/robustness/fairness/compliance results → champion selection under hard constraints. Seeds (`seed bigint`) make runs reproducible. **Consequences:** reproducible, auditable strategy evaluation; ESL-005 Monte Carlo extends the seed concept to `master_seed` for trial-level replay. **Revisit if:** evaluation moves to an external engine → persistence layer stays, execution moves out.

## ADR-007 — Decision Intelligence pipeline with founder-in-the-loop approval

**Status:** Accepted. **Context:** simulation output must become a governed, explainable, approvable recommendation — not an autonomous action. **Decision:** requests → option/sensitivity/explainability findings → `decision_recommendations` (`recommendation_status` draft→ready, `confidence`+`confidence_band`) → approval (`approval_status` pending→approved/rejected, `approved_by`, `approved_at`), with `founder_approval_required` as a first-class column on experiment-class tables. **Consequences:** no recommendation self-executes; the human gate is in the data model, not just the app. **Revisit if:** a class of low-risk decisions is authorized for auto-approval → encode as an explicit policy/ADR, keep the audit trail.

## ADR-008 — Monte Carlo architecture (ESL-005)

**Status:** **Accepted** (2026-07-22, broker ruling; promoted from Proposed after Phase 0 approval). **Context:** strategy evaluation needs large-N stochastic simulation with deterministic replay and convergence control. **Decision:** a persistence-first build — Phase 5A `monte_carlo_experiments` (config + lifecycle, `master_seed`, trial bounds, convergence/confidence targets, founder approval) attached to `strategy_evolution_experiments`; Phase 5B `monte_carlo_batches` (per-batch seeds derived from `master_seed`, results); worker/orchestration are later phases, out of the persistence scope. No enums (text+CHECK), RLS deny-by-default, matching ESL conventions.

**Two design decisions resolved (broker ruling 2026-07-22):**
1. **`approved_by` is `text`, not `uuid`.** Governance records identify *constitutional actors* (Founder, Steward, Executive Council, an AI organization/employee, a review board, a broker, a future external governance system), not necessarily a row in one table. A `uuid` FK would force every approval authority into a single identity table and couple the constitution to it. `text` keeps governance identities *logical*, loosely coupled, and future-proof. Formalized as a standard — see `standards/development_standards.md` §Governance identities (canonical format: `Founder`, `Broker`, `human:<name>`, `user:<uuid>`, `ai:<agent>`, `service:<svc>`, `committee:<name>`, `organization:<name>`). Principle: **governance identities are logical identities, not database identities; identity resolution belongs in the application layer, not the constitutional schema.**
2. **`updated_at` trigger — kept.** `monte_carlo_experiments` attaches `set_updated_at()`, consistent with the development standard (an `updated_at` column must have a maintaining trigger) and with `const_0001`, which closed that exact gap across the schema.

**Consequences:** reproducible, auditable simulations that plug into the existing ESL-004 → ESL-006 pipeline; ESL-005 introduces no new convention. **Revisit before build:** none outstanding — cleared the Phase 0 gate; both open decisions resolved above. ESL-005 5A resumes via the COS workflow (roadmap resume gate). **Supersedes:** nothing. **Superseded by:** — .

## ADR-009 — CA-001 Constitutional Auditor (independent assurance)

**Status:** **Accepted** (2026-07-23, Founder authorization via the Constitutional Recovery Package, Appendix A/D). **Context:** the platform needs an assurance function that evaluates repository changes, migrations, architecture, AI actions, releases, and runtime evidence for constitutional compliance — **independent of the Engineering organization that produces the work**. Without it, the implementer effectively self-approves. **Decision:** create **CA-001 Constitutional Auditor**, a ratified `constitutional_capability` owned by a new **Constitutional Assurance** organization, delivered **entirely by extending the existing `constitution` governance model** (see `audit/canonical_architecture_mapping_CA-001.md`): capability → `constitution.capabilities`, org → `constitution.ai_organizations`, binding → `ai_organization_capabilities`, findings → `agent_review_gates.findings`, events → `agent_event_log`, artifact registration → `artifacts`/`artifact_versions`. **No new tables, no parallel registries.** The Auditor may inspect, report, recommend, request remediation, and block only where an approved policy grants it; it may **never** implement, deploy, merge, ratify, modify production, audit its own authored work, or grant itself authority. **Consequences:** enforces separation of duties (implementer ≠ auditor) and the rule that **AI output alone is never ratification** — only human governance actors ratify. Evidence-vs-inference discipline is mandatory; missing evidence yields `Indeterminate`, never `Compliant`. **DB registration of the capability/org rows is a future reviewed migration — none applied by the CA-001 task (repository-first).** **Revisit if:** audit volume outgrows `agent_review_gates.findings` jsonb → consider a dedicated `constitution.audit_findings` table via a new ADR + migration. **Supersedes:** nothing. **Superseded by:** — .

**Status:** **Accepted** (2026-07-25, Founder ruling — "build all eight components," given twice). **Context:** BTRM-001 (Behavioral Trust and Resolution Model) was authored to Architecture Draft per the Founder's design directive (RPT-011 reconciliation + BTRM-001 spec, including a Phase-3 self-critique and an independent architecture-review-board challenge). (3) **Authorize the full eight-component build**, overriding the review board's reduced-increment recommendation, but preserving every safeguard the board conditioned approval on: the CI prohibited-inference/no-adverse-action guards and the explainability envelope ship *before* any advisory output reaches a user (board condition, BTRM-001 §13); build proceeds in dependency order (ENR-001 → BAE-001 → TM-001/CM-001 → ICOA-001 → RIE-001 → OCM-001/CS-001 → POL-001) as flag-gated, independently-reversible PROC-100 stages, each its own reviewable PR; TM-001 and CM-001 are implemented per their existing Proposed specs (reused, not redesigned — STD-004); no runtime code may reach an adverse action (eviction, denial, escalation, financial penalty) without `human_review_required`, per BTRM-001 §6/§11, until further Founder direction. **Consequences:** BTRM-001 is now a governing, Ratified enterprise capability; TM-001 and CM-001 gain their first real implementation (still Proposed themselves — this ADR ratifies BTRM-001 and authorizes their *use inside* BTRM-001, it does not itself ratify TM-001/CM-001 as standalone artifacts, which remain a future, separate ratification if needed); the intelligence hold remains fully in force outside this named set. **Supersedes:** ADR-012 §3, narrowly (scope above only). **Superseded by:** — .

## ADR-014 — Introduce the RP (Research Proposal) artifact family and the standing idea-to-constitution pipeline

**Status:** **Accepted** (2026-07-25, Founder ruling). **Context:** during Drive-synchronization planning, the Founder proposed a new intelligence-engine concept ("Decision Calibration Model™," DCM-001) plus six further reserved engine IDs (DAE/DVE/NIE/PIE/LIE/GIE-001), to be created directly as constitutional artifacts in Google Drive. Engineering flagged two problems: (1) minting new CRIDs in Drive inverts the platform's own stated hierarchy (GitHub is the constitutional source of truth; Drive is a generated, published mirror — per the existing "OwnerPilot Executive Dashboard" document and ADR-002's repository-first principle), and (2) "Decision Calibration" was not reconciled against existing artifacts (TM-001 trust, CM-001 confidence, and BTRM-001's own RIE-001/OCM-001 resolution-and-comparison components) before being proposed as new structure — precisely the duplication risk RPT-011 existed to catch for BTRM-001. The Founder agreed and proposed a permanent fix rather than a one-off: a dedicated, explicitly non-constitutional artifact family for capturing promising ideas while they await analysis, so novelty is not lost but governance is not bypassed either. **Decision:** (1) **Introduce the `RP-` (Research Proposal) CRID family** (MAP-001 §1, `research_proposal` object_type, CBS-001 `KNOWN_PREFIXES`). An RP is a lightweight, GitHub-authored capture of an idea — never itself constitutional, never `depends_on`-able by a constitutional artifact, never self-advancing. (2) **Establish the standing pipeline** any future intelligence-engine or architecture idea must follow before it can become a real CRID: **Research Proposal (RP) → Reconciliation memo (RPT-style, checking for duplication) → Architecture Draft → self-critique → independent architecture-review-board challenge → ADR → Founder ratification → constitutional artifact.** This generalizes, as a repeatable process, the exact path BTRM-001 already took (RPT-011 → BTRM-001 draft → §12/§13 critique/challenge → ADR-013). An RP "graduates" only when a new, properly-numbered artifact supersedes it through that full pipeline. (3) **Register RP-001 (Decision Intelligence), RP-002 (Decision Calibration), RP-003 (Portfolio Memory), RP-004 (Negotiation Intelligence)** as the first four captures under this family — Concept lifecycle, explicitly not constitutional, each carrying an overlap-check note (RP-002 in particular must be reconciled against TM-001/CM-001/BTRM-001's RIE-001/OCM-001 before any CRID like "DCM-001" is assigned). (4) **Reaffirm:** Google Drive remains a generated, downstream mirror of the GitHub constitution; no constitutional artifact — RP or otherwise — originates there. **Consequences:** future engine ideas have a safe place to live without weakening ratification discipline; the Drive knowledge library can safely mirror RP-001…004 as clearly-marked non-constitutional research, with no risk of them being mistaken for ratified architecture. **Supersedes:** nothing. **Superseded by:** — .

## ADR-015 — Ratify the RQS–OCM-001 reconciliation; amend BTRM-001 §3.7 with §3.7.1 (RQS as subordinate qualitative-first assurance framework)

**Status:** **Accepted** (2026-07-25, Founder ruling). **Context:** RP-005's "Outcome Projection Engine" and RP-006's "Recommendation Quality Score (RQS)" both proposed numeric confidence/probability output (settlement/litigation/collection probability; Fact/Legal/Negotiation/Outcome/Communication/Business confidence scores). BTRM-001 §3.7 had already ratified OCM-001 as strictly qualitative — support bands only, numeric probabilities prohibited absent validated datasets (Founder-gated). RPT-012 §2 flagged the conflict when RP-005 was captured; RPT-013 §1 found RQS reproduced the same conflict under a new name when RP-006 was captured. Raised twice without resolution, per the Founder's own assessment this was beginning to create constitutional ambiguity and implementation drift, and the Founder directed it be resolved now via a formal reconciliation memorandum rather than left parked. **Decision:** (1) **OCM-001 remains the controlling doctrine** — BTRM-001 §3.7 is not weakened or reinterpreted. (2) **RQS is retained**, redefined as a **qualitative-first, multidimensional recommendation-assurance framework** evaluating seven dimensions individually (factual grounding, legal analysis, objective alignment, alternative consideration, risk analysis, communication strategy, execution readiness) — never combined into one composite score. (3) **Quality and confidence are formally distinguished**: quality asks whether the required reasoning process was completed rigorously; confidence asks whether the evidence is sufficient and reliable; the two are never merged into a single figure (extending the same principle BTRM-001 §3.2/§3.4 already applies to TM-001/CM-001). (4) **Numeric telemetry is permitted internally only** — testing, calibration, benchmarking, model-version comparison, system-health monitoring — and may never independently approve, reject, rank, or execute a material recommendation, nor appear as a number in user-facing or decision-controlling output (no "87% recommendation quality"). (5) **No averaging away a critical failure**: a weak dimension is not diluted by strength elsewhere. (6) **BTRM-001 §3.7.1 is added** (new subsection; BTRM-001 version 1.0 → 1.1) codifying RQS in this subordinate, diagnostic-only form under OCM-001. (7) **RPT-012 §2 and RPT-013 §1 are formally closed** by **RPT-014** (this ADR's supporting reconciliation memorandum); RP-005 and RP-006 are annotated (not rewritten, per DOC-003 §9) to record which of their original provisions no longer describe the controlling design. **Consequences:** the RQS/OCM-001 conflict is resolved as a permanent constitutional position, not a one-off ruling — any future proposal for numeric recommendation scoring must reconcile against this ADR and BTRM-001 §3.7.1, not reopen the question from scratch. Gating and human review under BTRM-001 §6/§11 are unaffected. **Supersedes:** nothing (extends BTRM-001/ADR-013 and the qualitative mandate already in force). **Superseded by:** — .

## ADR-016 — Resolve the EA-101/OPOS/OPIL-EA-012 naming collision: a real three-layer stack, not one concept under three names

**Status:** **Accepted** (2026-07-26, Founder ruling). **Context:** RPT-013 §1 first flagged that RP-006's "OPOS" ("how OwnerPilot thinks") and "OPIL" ("everything routes through this") risked colliding with the already-Proposed **EA-012** (Constitutional Intelligence Layer) — one underlying concept apparently being given two new names. RPT-016 §1 found RP-008 escalated this to a **third** name, **EA-101** ("OwnerPilot Cognitive Architecture... How OwnerPilot Thinks"), whose own subtitle read as describing the same thing as OPOS's definition. Both reports flagged this as the single most urgent open item, blocking any Architecture Draft on RP-006 or RP-008 since every engine in those directives is described as reporting into whichever of the three turns out to be the real top-level artifact. RPT-016 §1 posed three explicit resolution options: (a) one concept, three redundant names; (b) a real three-layer stack (EA-101 = the architecture document; OPOS = the reasoning kernel it describes; OPIL/EA-012 = the intelligence layer that exposes it to workflows); (c) retire two of the three. The Founder was asked directly and chose (b). **Decision:** (1) **EA-101, OPOS, and OPIL/EA-012 are three distinct layers, not one concept under three names.** (2) **Provisional boundary definition** (to be formalized in each artifact's own future Architecture Draft, not created by this ADR): **EA-101** is the top-level, human-readable architecture document — the conceptual/descriptive layer stating the principles and posture of how OwnerPilot reasons, analogous in role to how EA-100 describes the application-layer architecture. **OPOS** is the reasoning kernel EA-101 describes — the operational ruleset/posture that actually implements EA-101's stated principles, sitting between the architecture document and the runtime layer. **OPIL, i.e. the already-Proposed EA-012** (Constitutional Intelligence Layer), is the runtime-facing intelligence layer that exposes OPOS's reasoning to product capabilities (BTRM-001 and any future consumer) — EA-012 does not need a new CRID for this role; its existing scope is reaffirmed as the bottom, workflow-facing layer of the stack. (3) **No new CRID is minted by this ADR.** EA-101 and OPOS remain RP-family content (RP-006, RP-008) until each is reconciled and separately carried through the full RP → reconciliation → Architecture Draft → self-critique → review-board challenge → ADR → ratification pipeline established by ADR-014 — this ruling only removes the naming ambiguity that was blocking that pipeline from starting, it does not itself ratify either artifact. (4) **RPT-013 §1 and RPT-016 §1's naming-collision findings are formally closed** by this ADR; both files are annotated (not rewritten, per DOC-003 §9) to record the closure and point here. **Consequences:** RP-006 and RP-008 may now proceed to a reconciliation memo/Architecture Draft structured as three distinct artifacts with the boundaries above, rather than remaining blocked on an unresolved ambiguity; any future proposal that reintroduces overlap between these three layers must reconcile against this ADR, not reopen the question from scratch. **Supersedes:** nothing (closes an open question RPT-013/RPT-016 raised; does not amend BTRM-001, EA-100, EA-012, or any other ratified artifact). **Superseded by:** — .

## ADR-019 — Ratify EA-101 v0.2; separately govern OPOS, Recommendation Object, Decision Graph, and the Financial Intelligence Engine; gate ECAP Wave-1

**Status:** **Accepted** (2026-07-26, Founder ruling). **Context:** EA-101 (OwnerPilot Cognitive Architecture) was authored to Architecture Draft (v0.1) with a self-critique and independent architecture-review-board challenge included, closing with five open items in §16: ratification, OPOS's CRID status, Recommendation Object/Decision Graph's CRID status, Financial Intelligence Engine design authorization, and ECAP Wave-1 refactor sequencing. The Founder ruled on all five together, following the ADR-013/ADR-017 precedent of resolving ratification and scope in one decision, after two rounds of drafted-package review that (round one) required registry validation of proposed identifier tokens rather than treating them as pre-decided, and (round two) confirmed final tokens and classifications following that validation: `OPOS-001` (rejecting no valid alternative — coined ID, consistent with MAP-001's coined-ID precedent), `RCO-001` (revised from an originally-proposed `RECOBJ-001`, rejected because it read as too close to the existing, heavily-used `REC-001` Recovery Kit prefix), `DECG-001`, and `FIE-001` — validated against `cbs.mjs`'s live registry (no `constitutional_id` or prefix conflicts found) before this ADR's canonical text was written. **Decision:** (1) **EA-101 version 0.2, incorporating the conforming amendments below, is ratified as the controlling target-state Cognitive Architecture.** Version 0.1 remains preserved as the Architecture Draft and historical predecessor — it is not independently ratified; v0.2 is the sole controlling text. (2) **OPOS, Recommendation Object, Decision Graph, and the Financial Intelligence Engine are each separately governed constitutional identifiers**, reserved through CBS-001's `PLANNED_CRIDS` registry process: **`OPOS-001`** (`object_type: doctrine` — direct precedent: DOC-001 already plays this exact role, a ratified operating doctrine standing beside its architecture counterpart EA-012, exactly as OPOS will stand beside EA-101); **`RCO-001`** and **`DECG-001`** (`object_type: standard` — the closest existing valid registry classification for "canonical semantic/structural requirements dependent artifacts must conform to"; no `constitutional_semantic_contract` type exists today and none is created by this ADR — a future taxonomy amendment remains available if ever needed, but is not required now); **`FIE-001`** (`object_type: enterprise_architecture`, consistent with EA-101/EA-102/EA-012's own classification for a bounded-scope architecture document). **Reservation establishes namespace and drafting intent only — it does not create, ratify, or authorize implementation of any of the four.** (3) **OPOS-001's future document is a proposed constitutional doctrine — a Doctrine Draft, not an Architecture Draft** (terminology matters: EA-101 and FIE-001 proceed through Architecture Draft; OPOS-001 proceeds through Doctrine Draft, consistent with existing canonical usage for `doctrine`-classified artifacts). OPOS-001's scope is broader than the reasoning sequence EA-101 §2 states: operating principles, mandatory reasoning stages, engine coordination rules, authority boundaries, failure and abstention behavior, human-review escalation, constitutional precedence, state transitions, auditability, learning restrictions, and how products/workflows invoke the intelligence layer — EA-101 defines *what* the Cognitive Architecture is; OPOS-001 defines the *rules under which it operates*. Neither may restate the other's content. (4) **The existing `recommendation_object_spec_v0.1.md` and `decision_graph_spec_v0.1.md` implementation specs remain drafting inputs and migration references only for RCO-001/DECG-001 — their provisions do not become constitutional merely through reservation of the future artifacts.** Each invariant in those specs remains subject to its own dedicated self-critique, independent challenge, reconciliation, and Founder ratification when RCO-001/DECG-001 are themselves drafted. (5) **A separate Financial Intelligence Engine Architecture Draft is authorized** — research and architectural drafting only, no implementation — covering financial projection, expected value, cost/cash-flow consequences, time horizons, sensitivity, uncertainty, assumptions and provenance, scenario comparison, tax/accounting boundaries, professional-review routing, and safeguards against false precision, built under ADR-015/BTRM-001 §3.7.1's qualitative-first disposition unmodified. **FIE-001 may not achieve de facto control of the Winning Strategy by assigning a composite financial score, mandatory ranking, veto, or optimization output that the Recommendation Synthesizer is required to accept without qualitative, multidimensional review** — financial expected value is one input among several, never an automatic winner-selector, the same posture ADR-015 already enforces against every other numeric-scoring temptation in this program. FIE-001 may contribute to RCO-001's future `financialAnalysisRef` only. (6) **ECAP Wave-1 refactor is approved as a planned, gated sequence.** Phase A — read-only analysis, documentation, interface mapping, and non-production characterization testing only; it may not alter production decision behavior, schemas, persistence, or interfaces — may begin immediately. ## ADR-017 — Ratify EA-102 as target-state architecture; authorize a reduced first-increment implementation; require an anti-corruption boundary pending EA-101/Recommendation Object/Decision Graph reconciliation

**Status:** **Accepted** (2026-07-26, Founder ruling). **Context:** EA-102 (Closed-Loop Learning Architecture) was authored to Architecture Draft per a Founder directive issued after an external "chief architect" AI review, itself carrying a self-critique and an independent architecture-review-board challenge (§10–11) that recommended a reduced first increment against the Founder's full eleven-component directive. The Founder considered five open items (ratification, build scope, EA-101/Recommendation Object/Decision Graph sequencing, EDIC, and the EA-101 `PLANNED_CRIDS` bookkeeping) and ruled on the first three together, following the ADR-013 precedent of resolving ratification and scope in one decision; EDIC is resolved separately in ADR-018, and the `PLANNED_CRIDS` bookkeeping is recorded as an administrative acknowledgment in STATUS.md, not an ADR. A drafted package was returned for architectural review before this ADR was entered, which surfaced that the originally proposed anti-corruption-boundary design was too code-specific and risked constitutionalizing an immature data shape; the revisions below were required and incorporated before this ADR's canonical text was written. **Decision:** (1) **EA-102 is ratified in full** (Architecture Draft → Ratified) as the controlling target-state Closed-Loop Learning Architecture. Architectural ratification and implementation authorization are formally distinct acts and must not be conflated for this or any future artifact. (2) **Implementation authority is limited to Outcome Analysis (§2.2) and Recommendation Evaluation (§2.3)**, together with only the minimum shared infrastructure, interfaces, adapter work, controls, provenance, testing, observability, audit, and migration support reasonably necessary to implement and validate those two components; such supporting work does not authorize implementation of any other EA-102 analytical capability. (3) **No additional new EA-102 capability is authorized for implementation by this ADR.** Capabilities already authorized under separate controlling artifacts — POL-001, EA-012, RPT-016, ADR-015, BTRM-001 — retain their existing authority, neither expanded nor revoked. (4) **Prediction/Confidence Calibration, Strategy Comparison Retrospective, and Knowledge Evolution remain ratified roadmap capabilities.** A documented readiness review may establish that one or more is eligible for implementation consideration but does not itself confer implementation authority; activation requires a separately recorded authorization. That review may never collapse into a universal composite readiness or recommendation-quality score — OCM-001 and the ratified qualitative-first RQS reconciliation (ADR-015, confirmed Accepted 2026-07-25, not superseded, canonically controlling) remain controlling, and no critical deficiency may be averaged away by strength elsewhere. (5) **EA-102 proceeds now against BTRM-001's existing shipped types** (`ResolutionOption`, `OutcomeComparison`, `OutcomeRecord`) rather than waiting on EA-101/Recommendation Object/Decision Graph, but only through the new §2.0 Anti-Corruption Boundary (Learning Representation Adapter) added to EA-102 by this ADR (version 0.1 → 0.2): a governed logical translation boundary (not necessarily one literal function) producing a versioned Normalized Learning Contract defined by semantic invariants — source/schema/adapter/contract provenance kept as independently versioned identifiers, stable correlation, a recommendation/strategy reference, predicted outcome and confidence kept separately represented, execution and observed-outcome information where available, observation status and temporal scope, known unknowns and dispute status, governing authorization/data-classification metadata where applicable, and original timestamps preserved with corrections handled as append-only/traceable supplements rather than overwrites — never a fixed constitutional field list; the exact schema lives in a subordinate, non-constitutional implementation specification. No EA-102 component may consume the BTRM-001 types directly, contain source-schema-specific translation logic, or treat those types as the permanent canonical Recommendation Object or Decision Graph; the adapter may translate, validate, and preserve provenance only — it may not select a winning strategy, alter recommendation substance, approve execution, determine correctness, or manufacture an observed outcome; and records failing normalization, provenance, required-field, or authorization validation must be quarantined or rejected, never silently admitted. (6) **RP-006/RP-008's reconciliation of EA-101, Recommendation Object, and Decision Graph is designated the next scheduled constitutional reconciliation** following completion of this package, subject only to intervening security, legal, production-critical, or Founder-directed priority. **Consequences:** EA-102 has a stable, ratified target state without speculative code against data that doesn't exist yet (BTRM-001 remains fully dark end to end); the anti-corruption boundary confines the coming RP-006/RP-008 migration to the adapter/contract layer rather than every analytical component, though any downstream change that migration does require must be documented, compatibility-tested, and justified as an exception rather than assumed away; RP-006/RP-008 reconciliation gains explicit priority rather than remaining an unstated shared dependency two workstreams (EA-102 and Chat-first BTRM-001 integration) were both quietly blocked on. **Revisit if:** RP-006/RP-008 reconciliation and any resulting Recommendation Object/Decision Graph ratification occurs (retarget the adapter, not the analytical components); a documented readiness review and separate activation authorization is sought for any roadmap capability. **Supersedes:** nothing. **Superseded by:** — .

## ADR-018 — Authorize hybrid EDIC architecture: synthetic-first now; real-matter ingestion and any training use require a separate governance package

**Status:** **Accepted** (2026-07-26, Founder ruling). **Context:** RPT-013 §1 first flagged EDIC's data-sourcing/privacy/IP question as unanswered and gating; it stayed open through RPT-016 and the Founder decisions recorded 2026-07-26, pending an explicit answer to whether the corpus is built from real client matters or synthetic scenarios. **Decision:** (1) **A hybrid architecture is approved** — synthetic and real-matter ingestion are two separately governed paths, never conflated. (2) **The synthetic path is authorized now**: schema design, provenance tagging, scenario generation, adversarial testing, evaluation, versioning, and benchmarking may proceed, subject to approved subject-matter, jurisdictional, provenance, safety, and evaluation constraints — this authorization does not permit indiscriminate corpus expansion, unreviewed external-source incorporation, or promotion of generated assertions into constitutional or operational knowledge. Synthetic provenance must at minimum distinguish authored versus model-generated content, source scenario/template, generator/model version, generation date, reviewer status, jurisdiction and time assumptions, whether the expected outcome is asserted/simulated/unknown, whether the scenario was adversarially modified, and licensing/source restrictions for any external material. (3) **The real-matter path is not authorized.** No record-level or matter-derived real client, tenant, financial, litigation, communication, operational, or outcome data may be ingested into EDIC — including data characterized as de-identified, pseudonymized, redacted, summarized, transformed, embedded, or aggregated from a small or identifiable population — unless separately authorized through a governance package addressing lawful use, consent, confidentiality, ownership, provenance, de-identification, re-identification risk, access, security, retention, deletion, and auditing, which must include documented review by qualified counsel covering confidentiality, consent, privacy, data ownership, IP provenance, de-identification, re-identification risk, broker obligations, and applicable statutory requirements before any real-matter path is proposed for activation. (4) **Synthetic scenarios must be expressly labeled synthetic** and may never be represented as observed outcomes; synthetic outcomes may be used for design, testing, challenge, benchmarking, and controlled evaluation but are not empirical evidence of real-world effectiveness, repetition of synthetic conclusions does not convert them into observed evidence, and Knowledge Evolution may not promote a rule solely because it performed well against self-generated scenarios. (5) **Synthetic and any future real-matter corpora must remain logically segregated**, independently permissioned, separately provenance-tagged, and queryable by source class; their records may not be silently blended in evaluation results. (6) **Storage or evaluation authorization does not authorize training use.** Use of any EDIC corpus for model training, fine-tuning, embedding generation, external model submission, vendor processing, or derivative dataset creation requires explicit authority under the applicable governance package, separate from ingestion/storage/evaluation authorization. **Consequences:** EDIC's foundational schema and pipeline work can start immediately without a privacy/IP decision made under time pressure; contamination of institutional knowledge by unvalidated synthetic conclusions is structurally blocked; real-case sourcing and any downstream training use both remain distinct, separately-reviewed future decisions rather than defaults. **Revisit if:** a real-matter governance package is drafted, counsel-reviewed, and separately approved. **Supersedes:** nothing. **Superseded by:** — .
