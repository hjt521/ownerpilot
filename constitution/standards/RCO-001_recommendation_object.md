# RCO-001 — Recommendation Object: Canonical Semantic Contract (Proposed)

> **Lifecycle: Proposed** (per STD-002 — specification recorded, not yet designed/ratified). **Revision 4** (2026-07-26), incorporating a genuine independent review-board challenge (the first non-self-administered review this document has received) covering RCO-001 and DECG-001 together. **Disposition: revision required before a coordinated ADR — granted via this revision.** The review authorized targeted drafting only; it does not authorize implementation, schema or persistence changes, ECAP Phase B, production use, merge, publication, ADR acceptance, or ratification. Still Proposed — this revision is not itself a ratification event; it is the fourth iteration of RCO-001's own drafting pipeline (standard draft → self-critique → a genuine independent review-board challenge → ADR → Founder ratification). **This document does not authorize implementation.**
>
> **Revision history:** Revision 1 (PR #299) first reconciled RP-006's 14-field and RP-008's 18-field proposals into semantic invariants. Revision 2 (PR #300) incorporated a Founder/architect review of Revision 1. Revision 3 (PR #303) incorporated RPT-019's joint reconciliation against DECG-001, amending §8's access-control guarantee to distinguish content access from validity-state access. **Revision 4 (this revision)** incorporates the genuine independent review-board ruling: expanded access-security minimum guarantees; a corrected Candidate definition (§1); presentation eligibility split from action authorization (§1); Corrected removed as a lifecycle state and reframed as a lineage event (§1, §2 invariant 14); strengthened human-review semantics (§2 invariant 9); a generalized explainability dependency (§2 invariant 8); invariant 10 reconciled with labeled assumptions/inferences/judgment; broadened confidence separation (§2 invariant 4); the RCO-001/DECG-001 circular dependency broken via a supporting-trace definition (§2 invariant 12); and a defined semantic identity for the DECG-001 reference. See the change matrix delivered alongside this revision for the full mapping.

## 0. What this is, and what it is not

**RCO-001 is the canonical semantic contract for a recommendation OwnerPilot produces** — what is delivered to a decision-maker (owner, or a future reviewer), not how it was reasoned to. That reasoning trace is DECG-001's job (§5 below). RCO-001 does not itself compute, rank, or select a recommendation; it is the shape a recommendation takes once the Recommendation Synthesizer (EA-101 §3) has produced one.

RCO-001 is **not** a database schema, a TypeScript interface, or an API contract. Those are implementation artifacts that must satisfy RCO-001's invariants; they are not this document. Per ADR-019 §2 and RPT-018 §0, reservation of this identifier does not itself ratify any schema — this Proposed draft is one iteration of RCO-001's own pipeline, not its conclusion.

## 1. Definitions and lifecycle states (normative)

These terms are used throughout §2's invariants and bind exactly as defined here. A future implementation may use different internal names, but must preserve these distinctions.

- **Validity** — whether a candidate Recommendation Object satisfies §2's invariants. Validity is binary at any given moment (valid or not), but is re-evaluated whenever a correction produces a new version (§2 invariant 14).
- **Completeness** — whether every field required for a given lifecycle state has either a resolved reference or an explicit unknown/missing marker (never a silent gap). Completeness is a precondition for advancing state, not a synonym for validity — a candidate can be complete (nothing silently missing) while still invalid (e.g., a required reference points to something that does not exist).
- **Review** — the human-review status inherited per invariant 9; a separate concept from validity/completeness. A Recommendation Object can be valid, complete, and still pending review. The review *trigger* (whether review is required) and the review *disposition* (what a reviewer decided) are distinct concepts — see invariant 9.
- **Presentation eligibility** — whether a Recommendation Object may be presented as an authoritative recommendation to an authorized decision-maker. Requires validity, completeness, and satisfaction of the inherited review requirement (§2 invariant 9); it is never a state a Recommendation Object grants itself.
- **Action authorization** — whether a recommended execution step (§2 invariant 7) may presently be performed. **Presentation eligibility does not itself confer action authorization.** Action authorization depends on separate external gates — legal, operational, user-approval, timing, or other review gates — that RCO-001 does not itself define, control, or grant. A Recommendation Object may be Authoritative (§1, below) and presentation-eligible while every one of its execution steps remains unauthorized pending those external gates.
- **Lifecycle states:**
  1. **Draft** — a candidate under internal construction or iteration. May be incomplete or invalid. Never presentation-eligible, never action-authorized, never decision-maker-facing.
  2. **Quarantined** — a candidate that failed validation (§2, invariant 13). Held for diagnostic and correction purposes only. Confers no authority under any circumstance and is never presentation-eligible or action-authorized.
  3. **Candidate** — valid and complete, with every constitutionally required reference resolved — including its supporting DECG-001 reference where one is required (§2 invariant 12) — but not yet eligible for authoritative presentation because required review, authorization, or other external gates remain outstanding.
  4. **Authoritative** — valid, complete, appropriately reviewed, and eligible for presentation to an authorized decision-maker. **Authoritative status does not itself authorize execution of any recommended action** — external legal, operational, user-approval, timing, and review gates governing action authorization remain fully in force and are never subsumed by reaching this state.
  5. **Superseded** — a prior version of a Recommendation Object, retained after a correction produced a new version (§2 invariant 14); no longer active; never deleted; remains retrievable.
  6. **Archived** — retained for historical/audit retrieval only, outside normal operational access paths.

**Correction is not itself a lifecycle state; it is a traceable lineage event** (§2 invariant 14). Correcting a Recommendation Object produces a new version, which must independently satisfy validity, completeness, and any required review before it may itself reach Candidate or Authoritative state — a correction confers no state by itself. The predecessor version transitions to Superseded, never deleted.

No implementation may skip a required state transition (e.g., Draft directly to Authoritative without passing through Candidate's completeness/validity checks), and no state may be self-assigned by the Recommendation Object itself — state transitions are governed by whatever upstream process (RIE-001, the Recommendation Synthesizer, or a human reviewer) is authoritative for that transition.

## 2. Semantic invariants (binding on any future ratified implementation)

Any concrete Recommendation Object realization must satisfy all of the following, using the lifecycle states and definitions in §1.

1. **Objective by authoritative reference, plus an optional immutable presentation snapshot.** The owner's objective is a reference into whatever produced it (ICOA-001 today). An implementation may additionally carry an immutable, point-in-time presentation snapshot of the objective's stated text for display purposes, provided the snapshot is explicitly labeled as a presentation copy — never a re-derivation or paraphrase substituting for the authoritative reference.
2. **Evidence, assumptions, unknowns, disputed facts, inferences, and judgment are each distinguished — never merged into one narrative block or conflated with each other.** Evidence cites specific resolved, provenance-classified items. Assumptions are explicitly labeled as assumptions, not evidence. Unknowns and missing information are named as gaps, never silently omitted and never fabricated to appear resolved. Disputed facts are preserved together with the dispute noted, never silently resolved in one direction. Inferences are labeled as derived, distinguishable from directly cited evidence. Judgment — a synthesizing assessment — is labeled as judgment, never presented as if it were fact or evidence. Each of these classifications is a permitted form of substantive content under invariant 10, provided it carries a supporting basis and stated limitations.
3. **Legal analysis, financial analysis, behavioral/negotiation input, and confidence each retain their own separate analytical provenance**, cross-referencing their source component, while permitting a traceable, human-readable synthesis that draws on more than one of them — provided the synthesis is itself explicitly labeled as a synthesis, and each underlying reference remains independently resolvable and is never displaced by the synthesis. `financialAnalysisRef` may point to FIE-001's output once FIE-001 exists and is itself ratified; until then it remains explicitly absent, not fabricated or approximated from other fields.
4. **Confidence is a distinct concept, never combined with or treated as a substitute for: predicted outcome; recommendation quality; correctness; legal eligibility; completeness; review status; readiness; presentation eligibility; or action authorization.** Each of these is separately represented. This broadens EA-102 §2.0's own rule (confidence never merged with predicted outcome) because Recommendation Object is exactly the kind of object where confidence is prone to being conflated with any one of these adjacent concepts if not stated explicitly and repeatedly.
5. **Risks and alternative strategies are grounded in references to already-produced structures** (RIE-001's `materialRisks`, OCM-001's compared alternatives). A derivative summary may accompany these references for presentation purposes, provided it is explicitly labeled as derivative and never replaces, overrides, or is resolvable independently of the authoritative reference.
6. **A communication artifact reference is authoritative; CS-001 owns communication structuring.** A derivative, clearly labeled summary may accompany the reference for presentation, but never substitutes for it.
7. **Execution steps and a review trigger are explicit, separate fields.** "What happens next" and "when should this be revisited" are different questions and must never share one field. An execution step's presence does not itself confer action authorization (§1) — that requires satisfaction of whatever external gates govern that step.
8. **An explainability reference is mandatory and must use the canonical explainability contract then governing OwnerPilot.** Initially, this is BTRM-001's `ExplainabilityEnvelope` shape. Any successor explainability contract requires governed compatibility and migration before RCO-001 may reference it; RCO-001 may not create a parallel explainability structure of its own.
9. **A human-review-required flag is inherited, never independently computed** by RCO-001 itself — it passes through unchanged from whatever upstream type (`ResolutionOption` or its successor) produced the recommendation, per BTRM-001 §6/§11. **RCO-001 may not independently downgrade, clear, or reinterpret an inherited review requirement.** Satisfaction, rejection, escalation, or supersession of that requirement must occur through a separately governed, traceable review event recording reviewer authority, scope, disposition, timestamp, and effect. The review *trigger* (this invariant) and the review *disposition* (the outcome of that governed event) are distinct fields and are never merged.
10. **No field may assert unsupported substantive content.** A substantive claim must either (a) trace to a resolved, provenance-valid reference, or (b) be explicitly classified as an assumption, inference, synthesis, or human judgment (per invariant 2), carrying its supporting basis and stated limitations. **Explicit labeling under (b) never converts unsupported speculation into valid content** — a labeled inference must still rest on some identifiable basis, even where that basis is itself uncertain. Intrinsic metadata (identifiers, timestamps, lifecycle state, version numbers) is self-describing structure, not a substantive claim, and is not subject to this rule.
11. **Provenance is carried as independently identifiable and versioned concepts** — the originating system, the originating artifact type, the schema version of the source, and RCO-001's own contract version are four distinct, separately trackable concepts. This invariant binds the semantic separation, not any literal field name — an implementation may name or structure these concepts however best fits its own schema, so long as all four remain distinguishable and independently versioned.
12. **An authoritative, material Recommendation Object — one that has reached Candidate or Authoritative state (§1) — must carry a resolved DECG-001 reference, never an embedded trace.** The DECG-001 reference required here resolves to a reproducible **supporting trace** whose terminal support node exists *before* the Recommendation Object advances to Candidate; the supporting trace may terminate at the Recommendation Synthesizer's output, an `OutcomeComparison`, a `ResolutionOption`, or another governed pre-recommendation terminal recognized by DECG-001's own standard. The Recommendation Object may later become a separately linked terminal or result node within a broader trace, but it is **not required to be part of the supporting trace it itself references** — any such reverse link is derivative and is never required to construct the supporting trace. This breaks what would otherwise be a circular dependency between RCO-001 and DECG-001. The reference must semantically bind, at minimum: the matter's identity; the terminal support node's identity; the relevant node version(s) or an explicit version-selection rule; the reconstruction/as-of time used; DECG-001's own contract version; and an authorization/access-policy reference where one is required. This binding may be stored, derived, hashed, tokenized, indexed, or materialized however an implementation chooses — this invariant fixes the semantic content of the reference, not its physical form. A Draft-state candidate is not required to carry a resolved DECG-001 reference, but may never advance to Candidate, be presented to a decision-maker, or reach an execution path without one.
13. **A candidate failing §2's invariants may exist only in Draft or Quarantined state (§1) and must never cross into Candidate, Authoritative, presentation-eligible, or action-authorized state.** Quarantine exists for diagnostic and correction purposes only and confers no authority under any circumstance.
14. **Original timestamps are preserved permanently.** Any correction, reclassification, or amendment produces a new, append-only version — never a silent overwrite (§1: correction is a lineage event, not a state). Each Recommendation Object carries an explicit active-version marker. A version resulting from correction must independently satisfy validity, completeness, and any required review before it may itself reach Candidate or Authoritative state — a correction does not inherit its predecessor's state. The corrected predecessor transitions to Superseded (§1), not deleted, and remains retrievable. Supersession is itself a traceable, timestamped event, distinguishable from ordinary version creation.

## 3. What this document deliberately does not fix

Consistent with the correction the Founder required of EA-102 §2.0 (no fixed field list) and with RPT-018 §2's explicit framing, this document does **not** enumerate a binding field-by-field schema. The illustrative mapping in `recommendation_object_spec_v0.1.md` remains an **external, informative, noncanonical, nonbinding** engineering reference — useful groundwork for a first implementation, but no field name, type, or structure in that document is itself a constitutional invariant, and it is neither inlined into this document nor deleted. Only §§1–2 above bind.

The following remain deliberately deferred to implementation, not fixed here as constitutional invariants: field-level schemas; API or query language; storage substrate; the graph-database decision (see DECG-001 §3 invariant 10); detailed migration mapping; notification delivery mechanics; cross-matter capability authorization; and the physical mechanics of state transitions. **The semantic corrections in this revision are not deferred** — they bind now, at the invariant level, regardless of how any of the above is eventually implemented.

## 4. Relationship to what already exists

RCO-001 does not replace `ResolutionOption` (RIE-001), `OutcomeComparison` (OCM-001), or EA-102 §2.0's Normalized Learning Contract. All three remain the real, shipped or ratified types today, and continue operating exactly as ratified. RCO-001 is the future canonical unification those would migrate toward once RCO-001 is itself ratified and a compatibility/migration specification (per ADR-019 §6) is separately approved — not a fourth parallel shape built independently of them, and not a retroactive invalidation of any of them before that migration is approved.

## 5. Relationship to DECG-001

RCO-001 is the recommendation; DECG-001 (its own future document) is the reasoning, dependency, alternative, evidence, risk, and lineage trace supporting it. A Candidate- or Authoritative-state RCO-001 references its DECG-001 **supporting trace** (invariant 12, §2); it never embeds DECG-001's structure. The supporting trace's terminal support node exists independently of, and prior to, the Recommendation Object that references it — RCO-001 does not need to already exist for its own supporting trace to be constructed, which is what makes the reference non-circular. Draft-state candidates are exempt from this requirement (§1, §2 invariant 12).

## 6. Versioning discipline

RCO-001's own document version (this revision: v0.4, still Proposed) is independent of EA-101's document version, EA-102's document version, DECG-001's document version, and any adapter/source-schema version. None of these are interchangeable, per the versioning-separation discipline the Founder required in ADR-017's final drafting controls and restated in ADR-019. This applies equally at the instance level: an individual Recommendation Object's active-version/correction/supersession lineage (§2, invariant 14) is independent of RCO-001's own document version — correcting a single recommendation does not imply or require a new document version of this standard.

## 7. Governance and validation posture

- No component may treat an RCO-001 realization as authoritative until RCO-001 itself is ratified via its own ADR.
- Any future implementation must reject or quarantine (never silently repair or admit) a candidate Recommendation Object that fails §2's invariants; a quarantined or Draft-state candidate must never cross into Candidate, Authoritative, presentation-eligible, or action-authorized state (§1, §2 invariant 13).
- RCO-001 may not become a policy engine: it carries references, labeled derivations, and inherited flags, and computes nothing itself. Any logic that selects a strategy, alters recommendation substance, approves execution, or determines correctness belongs upstream (Recommendation Synthesizer, RIE-001, OCM-001), never inside RCO-001's own contract.
- FIE-001 (once it exists) may populate `financialAnalysisRef` only; it may not, through that reference or any other mechanism, cause RCO-001 to treat a composite financial score as an automatic winner-selector — this restates FIE-001's own anti-de-facto-control clause (ADR-019 §5) as a constraint RCO-001 itself must also enforce on the consuming side.
- Review-requirement satisfaction, rejection, escalation, or supersession must always occur through the separately governed review event defined in §2 invariant 9 — RCO-001's own logic may never simulate, shortcut, or infer that event.

## 8. Constitutional-minimum persistence guarantees

Physical persistence and materialization strategy (whether RCO-001 requires its own dedicated storage or can be materialized as a read-time projection over already-shipped types) is deliberately left to the future ECAP Phase B migration specification (ADR-019 §6) and is **not** decided by this document. This section states only the minimum guarantees any eventual persistence approach must provide, regardless of how it is physically implemented:

- **Stable identity** — a Recommendation Object's identifier is stable across corrections and supersession; correcting a record never changes its identity, only its active version.
- **Reproducibility** — given the same upstream inputs and the same contract version, a Recommendation Object's derivation is reproducible for audit purposes.
- **Version preservation** — every version (original and corrected) is retrievable, per invariant 14.
- **Correction lineage** — the chain from an original Recommendation Object through any corrections to its currently active version is traceable end to end.
- **Graph association** — the DECG-001 supporting-trace reference (invariant 12) remains resolvable for the life of the Recommendation Object, including superseded versions.
- **Validation state** — a Recommendation Object's lifecycle state (§1) is itself persisted and auditable, not re-derived on demand from other fields.
- **Auditability** — every state transition and correction is logged in a form a human reviewer or CA-001-equivalent process can inspect.
- **Access control (expanded per the independent review-board ruling).** "Validity-state access is a purpose-limited, authorization-controlled metadata operation. It does not automatically authorize disclosure of the node's existence, exact lifecycle state, identifiers, substantive fields, diagnostics, or correction reason to the requesting consumer. Implementations must prevent substantive disclosure through metadata, errors, logs, timing, identifiers, or other side channels and must preserve the node version and observation time used for classification." Concretely, any implementation must provide:
  - **Purpose-limited authorization** — a validity-state read is authorized only for a stated diagnostic/traversal purpose (e.g., DECG-001 trace-validity flagging, per RCO-001 §2 invariant 12/DECG-001 §3 invariant 8), never as a general-purpose content-access grant.
  - **Minimum necessary lifecycle metadata** — only the metadata needed for the stated purpose is disclosed; an access-policy decision governs whether the exact lifecycle state or only a generic invalid/unavailable status is returned to a given consumer.
  - **No substantive disclosure through side channels** — errors, logs, timing, identifiers, counts, or any other observable behavior must not leak Quarantined/Draft substantive content.
  - **No privilege escalation through traversal** — a traversal process's validity-state read access must never be usable to obtain content access it would not otherwise hold.
  - **Auditable restricted-state reads** — every validity-state read of a Quarantined or Draft node is itself logged and inspectable.
  - **Version-specific or atomic observation** — a validity-state read preserves and reports the specific node version and observation time it classified against, never an ambiguous or shifting snapshot.
  
  This is a distinct, narrower operation from content access (Quarantined/Draft substantive content is never exposed through the same access path as Candidate/Authoritative material) and does not weaken that guarantee. (Amended per RPT-019 §2-3 and further strengthened per the independent review-board ruling's access-security minimum guarantees, §1 of that ruling.)
- **Historical retrieval** — Superseded and Archived records remain retrievable for audit, even though they are excluded from normal operational access paths.

These are constitutional minimums, not a schema. ECAP Phase B's migration specification determines how they are physically satisfied.

## 9. What remains undecided by this draft (for self-critique / review-board / Founder attention)

- The precise field-level schema (deliberately deferred, §3).
- The exact compatibility/migration specification mapping `ResolutionOption`/`OutcomeComparison`/the Normalized Learning Contract onto RCO-001 — required before ECAP Phase B per ADR-019, not authored here.
- Whether `financialAnalysisRef` should be a required-but-nullable field or an optional field entirely absent until FIE-001 ratifies — left open pending FIE-001's own Architecture Draft.
- The precise mechanics of state-transition authority (§1) — which upstream process is authoritative for each transition (Draft→Candidate, Candidate→Authoritative), and how a correction's resulting new version re-enters that sequence — left to the eventual implementation and migration specification, not fixed here as a constitutional invariant beyond "never self-assigned" (§1).
- The precise access-policy mechanism governing how much lifecycle-state detail (exact state vs. generic invalid/unavailable) is disclosed to a given consumer (§8) — an implementation and policy-configuration question, not fixed here beyond the minimum guarantees stated.

## 10. Self-critique

This revision's greatest risk remains invariant creep disguised as clarification, now compounded by the opposite risk introduced in fixing Revision 1: loosening an invariant too far in the name of flexibility. Each change was checked against both directions. Invariant 2's split into six distinguished categories (evidence/assumptions/unknowns/disputed-facts/inferences/judgment) is more operationally demanding than a simple "evidence and unknowns separate," and a future implementer may find some of the six collapse naturally in practice (e.g., assumptions and inferences may be hard to distinguish in some source data) — this is flagged rather than resolved, since collapsing them prematurely in this document would repeat an earlier revision's error of over-fixing shape too early. Invariants 3, 5, and 6's allowance for "labeled derivative synthesis" is the revision most likely to be exploited as a loophole for smuggling unlabeled inference back in as if it were a reference; invariant 10's reconciled no-unsupported-content rule is written to close that gap by requiring even labeled assumptions/inferences/judgment to carry a supporting basis, but a review board should continue to stress-test whether "explicitly labeled" and "supporting basis" are themselves enforceable or merely aspirational without a concrete labeling mechanism, which this document does not specify (deliberately — that is schema, not invariant).

**Record of the genuine independent review-board challenge (this revision):** the review found the prior revision's Candidate definition self-contradictory against invariant 12 (fixed, §1); found "execution eligibility" conflated presentation and action authorization (split, §1); found "Corrected" as a mutually exclusive state was structurally awkward against append-only correction handling (removed as a state, reframed as a lineage event, §1/§2 invariant 14); found the human-review flag underspecified against downgrade/reinterpretation risk (strengthened, §2 invariant 9); found the permanent BTRM-001 `ExplainabilityEnvelope` dependency too rigid for a document meant to outlive any one explainability shape (generalized, §2 invariant 8); found invariant 10 in unstated tension with invariant 2's labeled-content allowances (reconciled, §2 invariant 10); found confidence separation too narrow against the range of adjacent concepts it risks being conflated with (broadened, §2 invariant 4); and found the DECG-001 reference requirement circular as stated, since a Candidate-state RCO-001 required a DECG-001 reference while DECG-001's own drafting treated RCO-001 as a possible node within its traces (broken via the supporting-trace/terminal-support-node definition, §2 invariant 12, with a defined semantic identity for the reference). The review's access-security concerns (purpose limitation, side-channel prevention, no privilege escalation, auditability, version-specific observation, disclosure-granularity policy) are incorporated in full in §8's expanded access-control guarantee. This revision's disposition is: revision required before a coordinated ADR, granted by the changes above; a further genuine review of this revision itself has not yet occurred and remains a prerequisite before any ADR.
